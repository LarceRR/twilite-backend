# Twilite API

Модульный монолит на NestJS + Fastify. Clean Architecture внутри каждого модуля,
границы модулей повторяют bounded contexts домена.

## Запуск

```bash
cp .env.example .env          # copy .env.example .env — на Windows
docker compose up -d postgres redis
npm ci
npm run db:migrate
npm run db:seed               # тестовые данные: anna@twilite.dev / twilite-dev-password
npm run dev
```

API поднимется на `http://localhost:3000`:

| Адрес           | Что там                                   |
| --------------- | ----------------------------------------- |
| `/health`       | состояние сервиса, Postgres и Redis       |
| `/v1/docs`      | Swagger UI                                |
| `/v1/docs-json` | OpenAPI-документ для генерации клиента    |
| `/realtime`     | WebSocket, токен передаётся как `?token=` |

Всё приложение целиком (API + Postgres + Redis) поднимается одной командой:

```bash
docker compose up --build
```

## Конфигурация

Единственное, что нужно сделать руками, — создать `backend/.env`. Дальше ничего
экспортировать не надо: `src/config/load-env.ts` читает файл сам и делает это до
валидации конфига, поэтому `npm run dev`, `npm start`, `npm run db:migrate`,
`npm run db:seed` и `drizzle-kit` видят одни и те же переменные.

Правила простые:

- **Переменные процесса сильнее файла.** `set PORT=4000 && npm run dev` (cmd) или
  `$env:PORT=4000` (PowerShell) перебивают `.env` — Docker и CI ничего не теряют.
- **`.env.local` сильнее `.env`.** Личные секреты держите в нём, он в `.gitignore`.
- **Файл ищется вверх** от рабочей директории и от самого модуля, но не выше
  ближайшего `package.json`. Запускать можно и из `backend/`, и из корня репозитория.
- **CRLF и BOM срезаются.** Блокнот и другие Windows-редакторы больше не приклеят
  `\r` к `REDIS_URL` — раньше это ломало подключение без внятной ошибки.

Если переменных всё-таки не хватает, процесс падает на старте и в сообщении
перечисляет, чего не хватило и какие env-файлы он прочитал.

### Postgres и Redis в Docker, сервер локально

Рабочий сценарий: `docker compose up -d postgres redis` поднимает только
зависимости, порты проброшены на хост, поэтому в `.env` идут `localhost`-адреса из
`.env.example`. Сервис `api` из `docker-compose.yml` при этом не нужен — он ходит в
базу по внутренним именам `postgres` и `redis`.

## Команды

| Команда               | Назначение                              |
| --------------------- | --------------------------------------- |
| `npm run dev`         | dev-режим с перезапуском                |
| `npm run verify`      | типы + линтер + тесты (то же, что в CI) |
| `npm run db:generate` | SQL-миграция из схемы Drizzle           |
| `npm run db:migrate`  | применить миграции                      |
| `npm run db:seed`     | данные для разработки                   |

Схема — источник истины: после правки `src/database/schema` нужно выполнить
`npm run db:generate` и закоммитить SQL. CI проверяет, что они не разошлись.

## Структура

```
src/
  app/            композиционный корень (AppModule, health)
  bootstrap/      создание приложения, Swagger
  config/         чтение .env и env-переменные, провалидированные Zod при старте
  database/       схема Drizzle, миграции, seed
  infrastructure/ Redis, BullMQ, S3-совместимое хранилище, Sentry
  modules/        <контекст>/{domain,application,infrastructure,presentation}
  shared/         ошибки, контракты, guards, filters, утилиты
```

Внутри модуля зависимости направлены только внутрь:

- `domain` — сущности, value objects, доменные правила и **порты** репозиториев.
  Ничего не знает про NestJS, Drizzle и HTTP.
- `application` — сценарии (command/query handlers). Оркестрируют домен, не
  содержат бизнес-правил.
- `infrastructure` — адаптеры портов: Drizzle-репозитории, процессоры очередей,
  внешние провайдеры.
- `presentation` — контроллеры, DTO, WebSocket-шлюз.

Порты объявлены как символы (`SURFACE_OBJECT_REPOSITORY`), адаптер подставляется в
`*.module.ts`. Поэтому заменить Drizzle на что-то другое — это правка одного
провайдера.

## Ключевые решения

**Позицию объекта выбирает сервер.** Клиент присылает только `kind` и адресата;
ячейку определяет `spawnNearExisting` — поверхность растёт кластером вокруг уже
занятых ячеек. Уникальность ячейки гарантирует индекс в БД
(`surface_objects_cell_unique`), а не проверка в коде, поэтому два одновременных
запроса не займут одну клетку.

**`kind` — открытый реестр, а не enum.** Новый тип объекта добавляется в
`SurfaceObjectKind.ts` и сразу доступен: без миграций, таблиц и модулей.
Неизвестный тип от более новой версии клиента получает нейтральную политику.

**Оптимистичные блокировки.** У агрегатов есть `version`. Запись принимает
`version`, который видел клиент, и возвращает новый. Расхождение — `409`, клиент
перезапрашивает данные.

**Права проверяются в одном месте.** `JwtAuthGuard` и `SpacePermissionGuard`
зарегистрированы глобально; маршрут объявляет требование декоратором
`@RequirePermission('surfaceObject.create')`, публичный — `@Public()`.

**Realtime — канал доставки, не источник истины.** Клиент, пропустивший
сообщение, до-синхронизируется по HTTP. Подписка на пространство проверяется по
тем же правам, что и REST.

**Тяжёлое — в очередь.** Push-уведомления, письма, аналитика и переход
`Fading → Settled` идут через BullMQ. Регулярные задачи объявлены в
`RecurringJobs` с фиксированными `jobId`, поэтому несколько инстансов API не
задублируют расписание.

**Ошибки — единая иерархия.** Домен и приложение бросают `AppError`; глобальный
фильтр переводит их в один и тот же JSON-конверт с `kind`. Внутренние детали
неожиданной ошибки наружу не уходят.

## Тесты

```bash
npm test
```

Юнит-тесты лежат рядом с кодом (`*.spec.ts`) и покрывают доменные правила:
политику размещения, машину состояний, права, сборку промпта для AI. Они не
требуют ни базы, ни Redis.
